`go-yara` implements YARA parsing, compilation, and scanning in Go. Compatibility depends on the rule features and modules you use. Compile your own corpus and compare expected outcomes before replacing libyara.

## Engine comparison

go-yara provides an engine that can be embedded directly in a Go program without a native library. libyara and YARA-X provide other integration paths and a broader set of bundled file-format modules. Which fits an application depends on its rules, deployment constraints, and required output.

This comparison uses go-yara v0.8.0, libyara 4.5.8, and YARA-X 1.22.0, with sources reviewed on 2026-10-24. It describes implementation and integration differences; no cross-engine performance ranking has been measured for this page.

| Area | go-yara | libyara | YARA-X |
| --- | --- | --- | --- |
| Implementation and integration | Go library; no CGO or installed native engine. | C library with a C API; Go applications need a binding or another integration layer. | Rust engine with C and Go APIs. Its provided Go binding uses CGO and the YARA-X C library. |
| Condition execution | Go bytecode interpreter, fused operations, and specialized assertion programs. | Bytecode executed by a stack-based interpreter. | Compiles rule conditions to WebAssembly; native builds execute through Wasmtime. |
| Pattern searching | Shared Aho–Corasick searches, atom filters, regex/hex verification, and optional SIMD candidate filters. | Aho–Corasick atom searches followed by pattern verification. | Aho–Corasick candidate searches with specialized pattern and regex machinery. |
| Bundled modules | `hash`, `math`, `string`, and `time`; typed host data and callbacks. Native `pe` and `elf` parsers are not bundled. | Includes `pe`, `elf`, `dotnet`, and other analysis modules; availability can depend on the build. | Includes `pe`, `elf`, `dotnet`, and other analysis modules; availability can depend on build features. |
| Rule and API compatibility | Supports a YARA subset plus go-yara extensions described below. | Reference behavior for the project's libyara differential tests. | Targets YARA rule compatibility with documented language differences; its APIs differ from libyara's. |

The matching architecture has substantial overlap. Atom selection, verification strategy, condition execution, and result handling can each affect performance. go-yara's lack of a native dependency is a deployment property; it does not establish a scanning-speed advantage. The [performance page](/go-yara/performance/) explains its algorithms, measurements, and benchmark conditions.

For rules that depend on bundled PE or ELF analysis, libyara and YARA-X already provide those parsers. Exposing application-parsed data through a go-yara host module requires an adapter and compatible field semantics. Similarly, a rule accepted by one engine may need changes in another: YARA-X documents differences in regex escapes, base64 patterns, modifiers, and other constructs, while go-yara's differences are listed below.

## Supported rule features

Rules can use text strings, hex patterns with wildcards and jumps, regular expressions, string counts and offsets, condition operators, and rule references. The built-in modules are `hash`, `math`, `string`, and `time`. Their [function signatures](/go-yara/modules/#built-in-signatures) are generated from the documented release.

Native `pe` and `elf` parsers are not bundled. A structured host module can expose data supplied by your application, but it does not supply those parsers or make an existing native module interchangeable.

## Numeric and string behavior

| Operation | Behavior |
| --- | --- |
| Integer `math.min` and `math.max` | Compare integers as unsigned values, matching YARA. |
| Float or mixed numeric `min` and `max` | A go-yara extension: returns a float and uses signed numeric ordering. |
| `string.to_int` without a base | Autodetects decimal, octal, and hexadecimal consistently across platforms. `"0b10"` is undefined; use `string.to_int("10", 2)`. |
| String statistics on high bytes | Treats bytes as signed characters. Native results can differ where C `char` is unsigned. |
| Range statistics | Treats bytes as unsigned values. |
| Invalid ranges or conversions | Produces YARA's undefined value. A valid range beginning inside the input is truncated at EOF. |

For `min` and `max`, untyped external arguments retain the declared integer result contract unless a float argument is statically known. Use a float literal or a typed module field to select a float overload.

Native `string.to_int` behavior for a binary prefix can vary with the host C library and build. A native result on one machine is not a portable rule contract.

## go-yara extensions

`hash.sha512` and float overloads of `math.min` and `math.max` extend the libyara 4.5.x function set. The two-argument `math.deviation(offset, size)` computes standard deviation. YARA-compatible mean absolute deviation uses `math.deviation(offset, size, mean)` or `math.deviation(string, mean)`, with a floating-point mean.

Structured host modules, the `external` declaration syntax, and evidence extraction also need review when moving rules between engines. The `capture(...)` modifier and `evidence:` section add extraction behavior; other YARA implementations may reject that syntax.

## Streaming and compiled artifacts

The CLI's `--streaming` mode reports literal text-pattern matches without complete condition evaluation. Library `ScanReader` buffers the input, and sparse block scanning retains blocks. These APIs do not provide a single bounded-memory replacement for normal full-rule scanning.

Serialized go-yara programs use a project-specific format. They are not libyara compiled-rule files. Check the [upgrade rules](/go-yara/releases/#compiled-rule-caches) before sharing caches between versions.

## Testing a rule set

Compile the full rule set and investigate every rejected rule. Compare matched rule names on known positive and negative inputs, then check counts, offsets, undefined values, and module calls that your rules depend on. Include truncated and malformed files as well as ordinary samples.

If you find a difference, report a minimal rule, the input bytes or a small reproducer, both engine versions, and the observed results in a [GitHub issue](https://github.com/cawalch/go-yara/issues).
