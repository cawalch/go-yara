`go-yara` implements YARA parsing, compilation, and scanning in Go. Compatibility depends on the rule features and modules you use. Compile your own corpus and compare expected outcomes before replacing libyara.

## Engine comparison

go-yara provides an engine that can be embedded directly in a Go program without a native library. libyara and YARA-X provide other integration paths and a broader set of bundled file-format modules. Which fits an application depends on its rules, deployment constraints, and required output.

This comparison uses go-yara v0.11.0, libyara 4.6.0 / 4.5.8, and YARA-X 1.23.0 / 1.22.0, with sources and CLI measurements reviewed on 2026-11-19.

| Area | go-yara | libyara | YARA-X |
| --- | --- | --- | --- |
| Implementation and integration | Pure Go library; zero CGO, static binaries, and native Go cross-compilation. | C library with a C API; Go callers require CGO or an external wrapper. | Rust engine with C and Go APIs; the official Go binding wraps the native library via CGO. |
| Condition execution | Go bytecode interpreter with fused assertions, `assertionProgram` dataflow, and proximity two-pointer joins. | Stack-based C bytecode interpreter. | Compiles rule conditions to WebAssembly (executed via Wasmtime in native builds). |
| Pattern searching | Shared Aho–Corasick (byte-class tables), entropy-weighted atom selection, optional `GOEXPERIMENT=simd` Teddy/bounded-class kernels, and specialized hex/regex verifiers. | Aho–Corasick atom searches followed by pattern verification. | Aho–Corasick candidate searches with specialized pattern and regex machinery. |
| Bundled modules | `hash`, `math`, `string`, `time`, and pure-Go `pe` (`v0.10.0+`, `pe.overlay.*` in `v0.11.0`); typed Go host modules and callbacks. Native `elf`, `cuckoo`, and `dotnet` parsers are not bundled. | Includes `pe`, `elf`, `dotnet`, `cuckoo`, and other analysis modules depending on build flags. | Includes `pe`, `elf`, `dotnet`, and other analysis modules depending on build features. |
| Rule and API compatibility | Supports standard YARA rules plus Go-oriented extensions (`capture(...)`/`evidence:`, `external`, float `min`/`max`, `hash.sha512`); `WithStrictLibyaraCompatibility(true)` enforces libyara compile-time rejections. | Reference behavior for the project's libyara differential tests. | Targets YARA rule compatibility with documented syntax/regex differences and newer Rust APIs. |

### Strengths and trade-offs

- **Choose `go-yara` when** you need a pure-Go dependency (no CGO, static cross-compiled binaries, Wasm playground builds), direct Go host-module callbacks and zero-reflection `WithBorrowedEvidence(true)` JSON streaming, deterministic binary rule caches (`MarshalBinary`), or `WithStrictLibyaraCompatibility(true)` without shipping `libyara` shared libraries.
- **Choose `libyara` when** you need maximum legacy rule/module parity (`elf`, `dotnet`, `cuckoo`, full delayed-import/Authenticode `valid_on` surface) or existing C/Python tooling already built around libyara.
- **Choose `YARA-X` when** you want VirusTotal's next-generation Rust engine with bundled `elf`/`dotnet` parsers, WebAssembly-compiled conditions, and strict/modernized YARA-X rule diagnostics, and CGO/Rust native libraries fit your deployment model.

### Measured CLI comparison (2,000 mixed rules)

Measured on Apple M3 Max (`-p 4`, median of 3 cold CLI runs via `/usr/bin/time -l`) across 2,000 generated rules (1,000 literal, 500 regex, 500 hex) scanning 1 KB (compile + startup baseline), 128 MB clean (`16 × 8 MB`), and 64 MB match-heavy (`16 × 4 MB`, 3 matching rules per 4 KB):

| Engine | Compile + 1 KB (wall / peak RSS) | 128 MB clean (wall / peak RSS) | 64 MB match (wall / peak RSS) |
| --- | --- | --- | --- |
| `go-yara v0.11.0` (scalar) | `28.6 ms` / `37.3 MiB` | `31.7 ms` / `71.3 MiB` | `35.2 ms` / `60.3 MiB` |
| `go-yara v0.11.0` (`GOEXPERIMENT=simd`) | `27.9 ms` / `37.2 MiB` | `34.0 ms` / `70.8 MiB` | `35.2 ms` / `59.8 MiB` |
| `libyara 4.6.0` | `24.2 ms` / `12.5 MiB` | `85.0 ms` / `44.9 MiB` | `53.0 ms` / `30.2 MiB` |
| `YARA-X 1.23.0` | `152.0 ms` / `36.3 MiB` | `204.1 ms` / `101.0 MiB` | `170.5 ms` / `69.8 MiB` |

On this synthetic 2,000-rule workload, `libyara 4.6.0` has the lowest peak RSS (`12.5–44.9 MiB`) and fastest cold compile (`24.2 ms`), `go-yara v0.11.0` has the lowest total wall time on both 128 MB clean (`31.7 ms`) and 64 MB match-heavy (`35.2 ms`) scans, and `YARA-X 1.23.0` pays higher Wasm compilation startup (`152.0 ms`) and peak RSS (`101.0 MiB` on 128 MB clean). Different rule corpora, PE/ELF module workloads, or long-lived in-process scanners will shift these ratios.

The matching architecture has substantial overlap. Atom selection, verification strategy, condition execution, and result handling can each affect performance. go-yara's lack of a native dependency is a deployment property; it does not establish a scanning-speed advantage. The [performance page](/go-yara/performance/) explains its algorithms, measurements, and benchmark conditions.

For rules that depend on bundled ELF or .NET analysis, libyara and YARA-X already provide those parsers; native PE rules can use go-yara's pure-Go `pe` module starting in v0.10.0 within its [documented directory limits](https://github.com/cawalch/go-yara/blob/main/docs/pe-module.md). Exposing other application-parsed data through a go-yara host module requires an adapter and compatible field semantics. Similarly, a rule accepted by one engine may need changes in another: YARA-X documents differences in regex escapes, base64 patterns, modifiers, and other constructs, while go-yara's differences are listed below.

## Supported rule features

Rules can use text strings, hex patterns with wildcards and jumps, regular expressions, string counts and offsets, condition operators, and rule references. The built-in scalar/range modules are `hash`, `math`, `string`, and `time`; their [function signatures](/go-yara/modules/#built-in-signatures) are generated from the documented release. Starting in v0.10.0, go-yara also bundles a pure-Go `pe` module backed by `go-pe` (headers, sections, standard imports/exports and regex queries, `imphash`, resources, `version_info`, Rich headers, `pdb_path`, Authenticode metadata and offline integrity verification, `declared_extent`/`input_truncated`, `is_dotnet()`, and `pe.overlay.data_offset`/`data_size`/`certificate_size` in v0.11.0; see [PE module coverage](https://github.com/cawalch/go-yara/blob/main/docs/pe-module.md)).

Native `elf`, `cuckoo`, and `dotnet` parsers are not bundled, and delayed PE imports, flagged import queries, single-argument/mixed regex `pe.imports`, `signatures[i].valid_on(timestamp)`, and `signatures[i].file_digest` remain unsupported. A structured host module can expose data supplied by your application, but it does not supply those parsers or make an existing native module interchangeable.

## Numeric and string behavior

| Operation | Behavior |
| --- | --- |
| Integer `math.min` and `math.max` | Compare integers as unsigned values, matching YARA. |
| Float or mixed numeric `min` and `max` | A go-yara extension: returns a float and uses signed numeric ordering. |
| `string.to_int` without a base | Autodetects decimal, octal, and hexadecimal consistently across platforms. `"0b10"` is undefined; use `string.to_int("10", 2)`. |
| String statistics on high bytes | Treats bytes as signed characters. Native results can differ where C `char` is unsigned. |
| Range statistics | Treats bytes as unsigned values. |
| Invalid ranges or conversions | Produces YARA's undefined value. A valid range beginning inside the input is truncated at EOF. |

For `min` and `max`, untyped external arguments retain the declared integer result contract unless a float argument is statically known. Use a float literal or a typed module field to select a float overload.

Native `string.to_int` behavior for a binary prefix can vary with the host C library and build. A native result on one machine is not a portable rule contract.

## go-yara extensions

`hash.sha512` and float overloads of `math.min` and `math.max` extend the libyara 4.5.x function set. The two-argument `math.deviation(offset, size)` computes standard deviation. YARA-compatible mean absolute deviation uses `math.deviation(offset, size, mean)` or `math.deviation(string, mean)`, with a floating-point mean.

Structured host modules, the `external` declaration syntax, and evidence extraction also need review when moving rules between engines. The `capture(...)` modifier and `evidence:` section add extraction behavior; other YARA implementations may reject that syntax.

## Streaming and compiled artifacts

The CLI's `--streaming` mode reports literal text-pattern matches without complete condition evaluation. `ScanReader` and `MatchesReader` evaluate full rule conditions, regex, and hex patterns using bounded input windows. Retained occurrences and result data can grow with matches. Sparse block scanning retains supplied blocks.

Serialized go-yara programs use a project-specific format. They are not libyara compiled-rule files. Check the [upgrade rules](/go-yara/releases/#compiled-rule-caches) before sharing caches between versions, including the [v0.10.0 format-20 migration](/go-yara/releases/#upgrade-to-v0100). Use `WithStrictLibyaraCompatibility(true)` (v0.10.0+) when your pipeline requires libyara compile-time rejections for unreferenced strings or empty wildcard string sets.

## Testing a rule set

Compile the full rule set and investigate every rejected rule. Compare matched rule names on known positive and negative inputs, then check counts, offsets, undefined values, and module calls that your rules depend on. Include truncated and malformed files as well as ordinary samples.

If you find a difference, report a minimal rule, the input bytes or a small reproducer, both engine versions, and the observed results in a [GitHub issue](https://github.com/cawalch/go-yara/issues).
