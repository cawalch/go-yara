Compile a rule set once and reuse its `CompiledProgram`. Choose the scan API based on where the bytes live and whether you need complete match details or only a boolean answer.

<span id="choose-an-input-api"></span>

## Input APIs

| Input | API | Memory and evaluation behavior |
| --- | --- | --- |
| A byte slice | `program.Scan(data)` | Evaluates complete rules against the supplied bytes. |
| A bounded reader | `program.ScanReader(reader)` | Reads the entire input into memory, then evaluates rules. |
| A file path | `program.ScanFile(path)` | Opens the file and scans its contents. |
| Sparse memory blocks | `program.NewBlockScanner()` | Accumulates blocks; `Finish()` evaluates complete conditions. |

`ScanReader` is not a constant-memory streaming API. Block scanning also retains supplied block data. For inputs too large to retain, the CLI's [literal streaming mode](/go-yara/cli/#large-files-and-streaming) reports text-pattern matches, but does not evaluate rule conditions.

For sparse scans, provide each block's logical offset and set the logical file size when rules use `filesize`. If a pattern crosses a block boundary, supply overlapping bytes. The scanner does not reconstruct missing bytes between blocks.

<span id="choose-the-result-you-need"></span>

## Scan results

`Scan` returns a `ScanResult`. `MatchedRules` contains the rules whose conditions evaluated to true. `RuleResults` records boolean outcomes, while `Matches` records pattern occurrences. Pattern matches alone do not imply that the rule matched: its condition may still be false.

Use `Matches` when you only need to know whether any rule matched. Use `MatchingRules` when you need rule names and tags without the full evaluation map. These paths avoid work that detailed reporting would require.

Close a dedicated scanner when its worker finishes. A scanner is for sequential use; give each concurrent worker its own scanner. The compiled program can be shared. Do not mutate its configuration or call setters concurrently with scans, and keep input bytes unchanged for the duration of a scan.

## Cancellation and limits

Context-aware compilation and scan methods accept a `context.Context`. Cancellation is cooperative. For reader scans, cancelling the context cannot interrupt an underlying `Read` call that is already blocked; the reader or transport must provide its own deadline or close behavior.

For repetitive inputs, match limits can bound the number of recorded string occurrences. `WithMaxMatches` and `WithMaxMatchSpan` address different costs: occurrence counts and the bytes considered for an individual regex match. Limiting matches can affect conditions that depend on counts or offsets.

<p>See the <a href={`https://pkg.go.dev/github.com/cawalch/go-yara@${release.version}/compiler#Scanner`}>scanner API reference</a> for context-aware methods, hooks, and limit options.</p>

## Bind application data

External variables supply scalar values used by conditions. Structured modules supply typed fields, arrays, and dictionaries. Bind per-worker data on the scanner when concurrent scans need different values. The [modules guide](/go-yara/modules/#bind-structured-data) shows a complete binding example and explains missing values.
