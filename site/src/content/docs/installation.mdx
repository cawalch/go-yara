<p>The library requires Go {release.goVersion} or later. It has no CGO or libyara dependency. Prebuilt CLI binaries run without a Go installation.</p>

## Add the library

In an existing Go module, pin the documented release:

<Code code={`go get github.com/cawalch/go-yara/compiler@${release.version}`} lang="sh" />

Then follow the [complete Go example](/go-yara/quickstart/). The public entry point is the `compiler` package.

## Download the CLI

Choose an archive for your operating system and CPU. Extract it and place the `go-yara` executable on your `PATH`. On Windows, the executable is `go-yara.exe`.

<p>Compare the archive's SHA-256 digest with <a href={`https://github.com/cawalch/go-yara/releases/tag/${release.version}`}>the checksums attached to the release</a>. The release also includes the checksum signature and certificate.</p>

Run `go-yara --help` to confirm the executable is available, then [scan a file](/go-yara/cli/#scan-a-file).

## Build from source

With Git and a supported Go toolchain installed:

<Code code={`git clone https://github.com/cawalch/go-yara.git
cd go-yara
git checkout ${release.version}
go build -o go-yara ./cmd
./go-yara --help`} lang="sh" />

Building with `-o go-yara` gives the executable the name used throughout these docs. On Windows, use `-o go-yara.exe`.

## Optional SIMD build

With Go 1.27 or later, the experimental SIMD build can accelerate parts of literal matching and case folding:

```sh
GOEXPERIMENT=simd go build -o go-yara ./cmd
```

Scalar paths remain available on unsupported platforms and when SIMD is disabled with `GODEBUG=simd=0`. Measure your rule set and inputs before choosing a build; [performance guidance](/go-yara/performance/) explains what to compare.

## Browser and embedded runtimes

The [browser playground](/go-yara/quickstart/#browser-playground) runs the documented release locally in a Web Worker. It downloads its runtime when you start a scan. Rules and input bytes stay in the browser. The build checks the playground in Chromium, Firefox, and WebKit before publication.

<ArchitectureDiagram kind="browser" />

The browser build contains the Go runtime and go-yara's compiler and scanner. A rule still compiles to go-yara bytecode inside that engine; it is not compiled into a separate Wasm module. Input bytes are copied into Go memory. The playground accepts 16 KiB of rule source and 1 MiB of input, with a three-second operation deadline and a hard 128 MiB Wasm linear-memory ceiling. Browser overhead is additional.

Go's [browser Wasm support](https://go.dev/wiki/WebAssembly) needs a matching `wasm_exec.js`. A [WASI reactor](https://go.dev/blog/wasmexport) instead needs a host that supplies WASI imports and initializes the module before calling its exports. A Go application can embed the library directly without either runtime layer.

The playground displays at most 100 rule names and 200 occurrences within a 64 KiB response. These are display limits: conditions evaluate against the full scan. A timeout or runtime failure produces no complete result, and the worker is discarded. Native file paths and memory mapping are not part of this byte-buffer interface.

The earlier [runtime spike](https://github.com/cawalch/go-yara/tree/main/site/spikes/wasm) also tested a WASI command and a minimal reactor against v0.8.0. WASI integration remains experimental; there is no supported host ABI or general-purpose JavaScript package. The playground is a documentation tool, with its own small interface and limits.
